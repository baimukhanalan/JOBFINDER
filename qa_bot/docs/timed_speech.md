# Контур тайминга для Read and Speak

`TimedSpeechPipeline` разделяет подготовительный экран и экран записи. Это
обязательное условие для короткого таймера: на событии `Speak Now` запрещены
TTS, LLM, SQLite lookup, конвертация MP3 и ожидание готовности.

## Жизненный цикл

1. При первом достоверном `Listen Carefully`/экране подготовки вызывается
   `prepare(TimedSpeechRequest(...))`. Метод возвращает `session_id` сразу, а
   работа продолжается в одном фоновом worker.
2. Worker сначала ищет точное совпадение в `SpeechReplayBank`. При совпадении
   внешний или локальный TTS даже не создаётся. Для нового Read and Speak ответ
   равен видимому тексту, поэтому локальный macOS TTS создаёт MP3/WAV без LLM и
   сохраняет источник вопроса, профиль и тест в SQLite.
3. WAV полностью проверяется и передаётся `sink.arm(...)`. Только после этого
   состояние становится `ARMED`. Оркестратор должен проверить его ещё на экране
   подготовки через `wait_until_armed`; это ожидание нельзя переносить на
   `Speak Now`.
4. При `Speak Now` вызывается `speak_now(session_id)`. Метод только запускает
   заранее вооружённый sink. Если ответ ещё не готов, попытка немедленно
   останавливается вместо опоздавшего или случайного звука.
5. `listen_carefully`, `audio_armed`, `speak_now_started` и ошибки пишутся в
   append-only JSONL отдельным writer-потоком. В событии есть profile/test/question,
   SHA-256 аудио, источник `generated`/`replay`, время подготовки и задержка старта.

Для браузерного direct-mic механизма нужно передать sink, который в `arm` заранее
декодирует WAV в `AudioBuffer`/`MediaStreamDestination`, а в `play` вызывает
только `AudioBufferSourceNode.start()`. Встроенный `PreloadedAfplaySink` нужен
для локальной диагностики; акустический вывод через динамики не является
надёжным способом подачи сигнала в микрофон браузера.

## Измеренный локальный бюджет

Контрольный прогон на macOS с новым предложением и системным TTS:

- постановка в worker: 0,278 ms;
- генерация, MP3/WAV, SQLite и arm: 622,7 ms;
- уже вооружённый `speak_now`: 0,015 ms с тестовым memory sink.

Это измерение подтверждает разделение критического пути, но не измеряет задержку
конкретной страницы assessment. Browser watcher должен отдельно журналировать
момент появления `Speak Now`, вызов `start()` и фактическое начало ненулевого
сигнала. Граница по умолчанию — 250 ms; превышение считается ошибкой попытки.

## Ограничения

- Новый вопрос должен появиться хотя бы примерно за 0,7–1,0 секунды до записи,
  иначе первый локальный TTS может не успеть. Точное совпадение обычно готовится
  значительно быстрее.
- Если текст вопроса становится доступен только одновременно со `Speak Now`,
  Read and Speak нельзя надёжно решить генерацией в этот же момент. Нужен уже
  известный exact-match либо более ранний источник данных страницы.
- `PreloadedAfplaySink` прогревает файл, но всё равно создаёт процесс. Для live
  прогона предпочтителен заранее декодированный WebAudio sink.
- Переход на следующий вопрос разрешается только после подтверждения страницы,
  что ненулевой звук был принят; `player_id` сам по себе этого не доказывает.
