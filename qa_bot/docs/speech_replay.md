# Точная память речевых ответов

`SpeechReplayBank` хранит связь между точным текстом вопроса, текстом ответа,
оригинальным MP3 и WAV для браузерного аудиовхода. Первый показ вызывает локальный
macOS TTS один раз. Все последующие показы того же вопроса возвращают те же файлы
и не вызывают ни TTS, ни LLM. Изменение слова, регистра или пунктуации создаёт другой
ключ; меняются только Unicode NFC и повторяющиеся пробелы.

SQLite-таблица `speech_answers` хранит контрольные суммы и исходный профиль,
тест и номер вопроса. `speech_usage` добавляет отдельную строку при каждом
воспроизведении, поэтому можно установить, на каком профиле MP3 был создан и
на каких профилях повторно использован. Перед каждым повтором проверяются
контрольные суммы MP3 и WAV. Повреждённый или подменённый файл останавливает поток.

`MacOSLocalTTS` использует системный `say`, переводит результат в mono PCM16
16 kHz и локально кодирует MP3 через LAME. Внешний TTS и API-ключ для этого пути
не нужны. `ChromiumFakeMicrophone` атомарно помещает полученный WAV
по стабильному пути и отдаёт три launch-аргумента Chromium. Проверка в настоящем
Chromium подтвердила, что страница получает ненулевой сигнал через
`getUserMedia({audio:true})`.

Для `SVAR-01 / Read and Speak` ответ детерминирован: `read_aloud_answer` берёт
видимый текст предложения без перефразирования. LLM для такого задания не нужен.
Для других устных типов сначала требуется точный утверждённый текст ответа.

## Локальное распознавание без внешнего API

Для входящего аудио используется локальный ONNX-runtime установленного Natively.
Основная модель — `distil-whisper/distil-small.en`: на контрольной записи она
вернула полную фразу дословно, тогда как обе проверенные Moonshine-модели потеряли
последнее слово. Исходный WAV сохраняется независимо от результата STT, поэтому
ошибка распознавания не уничтожает материал и не приводит к случайному ответу.

```bash
PYTHONPATH=src .venv/bin/python -m qa_bot.adapters.stt.natively_local \
  runs/speech/e2e-local/browser-input.wav
```

`DirectAudioLoopback` предназначен для `Listen and Repeat`: он подаёт услышанный
браузером аудиофайл непосредственно в `getUserMedia` без STT/TTS и без изменения
слов. Механика выключена по умолчанию, ограничена разрешённым хостом и путём и
останавливается при любой ошибке. Аудио загружается и декодируется ещё на экране
прослушивания; после появления `Speak Now` запускается уже готовый буфер.
Ошибки загрузки используют ограниченное число попыток с exponential backoff;
после исчерпания лимита вопрос переходит в terminal failed. История ошибок имеет
фиксированный предел, а отсутствие подготовленного буфера не создаёт отдельную
ошибку каждые 50 ms. Если запись уже началась, а буфер ещё не готов, вопрос
один раз помечается `recording_unprepared` и поздний replay не запускается.
Если browser `fetch()` не может прочитать разрешённую signed media URL,
`DirectAudioLoopback` один раз в рамках той же ограниченной попытки использует
`XMLHttpRequest` с `responseType=arraybuffer`. Успешный XHR не увеличивает retry
counter. Динамическое появление или изменение `audio/src` отслеживается напрямую
через MutationObserver, поэтому подготовка начинается до resource timing entry.
Для вопросов, где ответ отличается от записи, используется цепочка
«сохранить WAV → локальный STT → проверенный ответ → MP3/WAV».

`DirectSpeechBridge` покрывает заранее известный ответ и точный повтор из банка.
Его init-script устанавливается до кода страницы, перехватывает
`getUserMedia({audio:true})` и возвращает `MediaStreamDestination`. При маркере
`Listen Carefully` скрипт вызывает локальные `/prepare` и `/audio`, проверяет
SHA-256 WAV и декодирует его. При `Speak Now` остаётся только запуск буфера;
browser test проверяет ненулевой сигнал в окне 200 ms и задержку старта менее
75 ms. Канал требует браузерного разрешения `local-network-access` для HTTPS →
`127.0.0.1` и фиксированного payload при установке init-script. Поэтому новый
неизвестный вопрос нельзя безопасно решить одним этим скриптом: ему нужен
локальный resolver или заранее подготовленный ответ.

`DynamicReadAloudBridge` убирает это ограничение только для детерминированного
Read and Speak, где ответ обязан дословно совпадать с видимой фразой. Он работает
с одним явно заданным корнем текущего вопроса, отдельными селекторами инструкции,
фразы и фазы и обязательным site question id. Фраза должна оставаться одинаковой
минимум три наблюдения; затем `/prepare` и `/audio` выполняются до `Speak Now`.
После смены site id или фразы старый запрос отменяется, старый источник
останавливается, а новый вопрос получает отдельный epoch. `AudioContext` и один
перехваченный `MediaStream` сохраняются между вопросами. Два видимых корня,
дубликат узла фразы, неизвестная инструкция, отсутствие id, поздний ответ старого
epoch или `Speak Now` до состояния armed не приводят к воспроизведению. Последний
случай явно журналируется как `recording_unprepared`, чтобы оркестратор мог
перезапустить контролируемую попытку, а не принять молчание или поздний звук.

Для собственного Chromium `BrowserController(local_network_origins=(...))`
выдаёт `local-network-access` только явно указанному HTTPS-origin, который уже
есть в allowlist. Это позволяет localhost speech bridge работать в headless
режиме и при заблокированном экране; разрешение не распространяется на другие
сайты.

Для страницы без специальных `data-qa-*` атрибутов включается
`auto_detect=True`. В этом режиме инструкция должна дословно совпасть с
`Read the given sentence out loud.`, а видимый экран должен содержать ровно одну
фразу длиной 15–1000 символов и не менее четырёх слов. Счётчики вида
`Question 1 of 5`, `Q 1/5` и `1 / 5` не считаются фразами и вместе с hash фразы
образуют identity, если site question id отсутствует. Section, timer, точные
phase и submit/navigation labels исключаются. Две равноправные фразы, инструкции,
счётчика или фазы переводят состояние в blocked без подготовки и воспроизведения.

Подготовленный init-script можно выдавать через `qa-injection-server`. Сервер
привязывается только к `127.0.0.1`, отдаёт один неизменяемый JS по точному пути и
проверяет точные `Origin`, `Host` и заголовочный token. CORS/PNA разрешены только
для этого сочетания; ответ помечен `no-store`, `nosniff` и SHA-256. Token читается
из `QA_INJECTION_TOKEN` и не появляется в URL, теле ответа, startup-сообщении или
HTTP log.

`SpeechAnswerFlow` теперь покрывает три разных маршрута без смешивания данных:

- Read aloud: видимый текст становится ответом дословно;
- Listen and repeat: оригинальный MP3 становится микрофонным WAV, а STT хранится
  только как метаданные и не может изменить звук;
- Listen and answer / speak topic: сохранённый WAV распознаётся локально, текстовый
  решатель возвращает ответ, затем точный банк делает TTS только при первом показе.

Для Listen and answer / speak topic поиск сохранённого ответа выполняется **до**
вызова решателя. Точный повтор берёт исходный текст ответа и те же MP3/WAV,
добавляет запись об использовании и работает даже без подключённого решателя
или TTS после перезапуска процесса. Повреждение артефакта останавливает поток
до вызова решателя и подачи звука. Если вопрос содержит входящее аудио, STT пока
выполняется для определения его содержания; инструкция и полная расшифровка
вместе образуют ключ. Одинаковая инструкция с другой расшифровкой не является
совпадением. Запись в `speech_usage` означает подготовку к воспроизведению,
а не подтверждённое принятие записи сайтом.

`SpokenTextSolver` формирует из вопроса и проверенной расшифровки отдельный
контентный hash, принимает только актуальный JSON `kind=text`, confidence ≥ 0.9
и минимальное число слов. Stale, short, low-confidence и abstain не доходят до TTS.

`SpeechReplayBank.import_existing` добавляет исходный MP3 прошлого варианта в
контентный банк без вызова TTS. Файл копируется, декодируется в WAV, оба артефакта
получают SHA-256 и источник профиль/тест/вопрос. При точном повторе возвращаются
те же байты; конфликт текста ответа или повреждение файла останавливает поток.

Для переноса аудиобайтов из управляемого браузера в локальный банк предусмотрен
`qa-capture-audio`. Сервер слушает только `127.0.0.1`, принимает один явно
разрешённый HTTPS-origin, требует случайный токен из `QA_CAPTURE_TOKEN`, ограничивает
размер и имя файла и возвращает SHA-256. Это сохраняет оригинал до STT и позволяет
доказать, что повторно использован тот же файл.

Оригинальные записи Listen and Repeat сохраняются отдельно через
`qa-prompt-capture`. `DirectAudioLoopback` передаёт уже загруженные байты в этот
localhost endpoint фоновым запросом после подготовки аудиобуфера. Запрос не
ожидается в критическом пути: искусственно замедленная на 400 ms запись manifest
не изменила задержку запуска при `Speak Now`. Сервер принимает только точный
HTTPS Origin, точный разрешённый media host, разрешённый фрагмент пути и локальный
token. В `prompt_manifest.jsonl` записываются SHA-256, локальный относительный
путь, профиль/тест/вопрос и host/path без query string; подписанный URL и token
не сохраняются.

## Подготовить один ответ

По умолчанию первое появление вопроса озвучивается локально. Значение ответа
сохраняется вместе с MP3/WAV, а точный повтор использует те же байты.

```bash
PYTHONPATH=src .venv/bin/python -m qa_bot.speech_runtime \
  --question 'The world is such a small place.' \
  --source-profile 'profile-01' \
  --source-test 'TP-001' \
  --source-question 'TP-001-SVAR-READ-004'
```

Результат содержит `mp3_path`, `microphone_wav`, SHA-256 и источник
`generated`. Повтор той же команды возвращает `source: replay`,
`provider_generation_requests: 0` и `local_generation_requests: 0`.

ElevenLabs оставлен только как явный совместимый режим `--tts-provider elevenlabs`.
В таком режиме ключ читается только из `ELEVENLABS_API_KEY`; без этого флага
контрольные и последующие прогоны не обращаются к ElevenLabs.

Команда только готовит аудио и браузерный файл. Для живого сайта всё ещё нужен
проверенный адаптер его DOM, жизненный цикл Record/Stop/Next и подтверждение
результата записи. Текущий production executor этого не делает.

## Что перенесено из механики Natively

- захват аудио, STT и подготовка ответа разделены интерфейсами;
- 16 kHz PCM используется как общий внутренний формат;
- финальный результат отделён от частичной расшифровки;
- модель/провайдер могут быть прогреты и заменены без изменения банка;
- очередь и ошибки STT не уничтожают исходную запись;
- повторный точный вопрос обслуживается локальным артефактом.

Natively использует локальный Whisper в отдельном worker, VAD, ограниченную
очередь, watchdog зависшего partial-pass и context prompt. Эти принципы подходят
для следующего локального STT-провайдера. Код Natively в проект не копировался.
