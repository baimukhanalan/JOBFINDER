# Residential proxy — домашний IP как egress для сервера (turnkey)

Пускает автоматизацию сервера (co-pilot / заполнение форм) через **домашний интернет** машины
владельца, чтобы дойти до ATS, которые блокируют датацентр-IP (Teleperformance/iCIMS, Kelly/Akamai,
reCAPTCHA-Greenhouse). Maximus/Avature работает и с сервера — ему это не нужно.

## Владельцу (turnkey — открыл, скачал, запустил)
**Страница:** `https://proxy.systeam.kz/<TOKEN>/` (токен = секрет доступа; забукмарь). На ней авто-
определяется ОС и две кнопки:
- **Скачать и подключить** → Windows `win.exe` (двойной клик, без терминала) · macOS `mac.command`.
  Запустил → ставит автозапуск при входе и уже работает в фоне (окно не нужно держать открытым).
  Несколько машин можно подключить одновременно — сервер ротирует их IP (слоты 8120–8129, до 10).
- **Отключить** → `win-off.bat` / `mac-off.command` — останавливает и убирает из автозапуска.
Капча на сайте → открыть noVNC `https://jobs.systeam.kz/vnc/` и решить; форму заполняет бот.

## Как устроено
```
Машина: агент (Go, один бинарь) — обратный SSH-туннель на сервер как юзер `tunnel`
        + встроенный HTTP-прокси; занимает первый свободный слот 127.0.0.1:8120..8129 (loopback)
Сервер: co-pilot берёт слот-прокси -> трафик уходит в интернет ЧЕРЕЗ машину (residential IP)
```
`proxy_pool.next_proxy()` пробит весь диапазон, ротирует ВСЕ живые слоты round-robin и предпочитает
их над Bright Data; отключилась машина — её слот пропадает из пробы и перестаёт использоваться;
слотов ноль — откат на Bright Data. Автопереподключение — экспоненциальный backoff (потолок 60с).

## Сборка / деплой (разработчику)
`bash build_and_deploy.sh` — кросс-компилит клиент (`client/`, встраивая `dist/tunnel_key`), генерит
установщики + страницу и деплоит в `/var/www/proxy-dist/<token>/`. Требует `go`, `dist/tunnel_key`,
`dist/token`. Клиент один: `client/main.go` (+ `notify_*`) — режимы `--install` (по умолчанию) /
`--run` / `--uninstall`.

Одноразовая серверная настройка (НЕ в скрипте, сделано вручную):
- юзер `tunnel` (nologin, пароль заблокирован) + `~/.ssh/authorized_keys`:
  `restrict,port-forwarding,permitopen="127.0.0.1:1",permitlisten="127.0.0.1:8120"…"8129",command="/bin/false"`
- nginx-vhost `proxy.systeam.kz` + `certbot --nginx -d proxy.systeam.kz`; отдаёт ТОЛЬКО `/<token>/`,
  всё прочее → `444`; `00-default-drop` default_server оставлен на месте.

## Безопасность (см. глобальный CLAUDE.md, инцидент 2026-04-16)
- Серверный конец туннеля — **только loopback 127.0.0.1:8120..8129** (`GatewayPorts no`), недоступен
  снаружи; наружу порт НЕ открыт.
- SSH-юзер `tunnel`: ключ-only, nologin, пароль заблокирован. `authorized_keys` даёт **только**
  обратные форварды в этот loopback-диапазон (`permitlisten`) — ни шелла, ни `-L` (`permitopen=…:1`),
  ни любого другого порта/команды. Проверено: `-L`/`-R` вне диапазона/шелл отклоняются.
- Клиент **пинит host-key сервера** (ed25519 в `main.go`) — MITM невозможен.
- Страница/бинари отдаются ТОЛЬКО по секретному токен-пути по HTTPS; корень/чужой путь/чужой хост → 444.
- **Остаточный риск:** бинарь/ключ = секрет; утёкший ключ может открыть обратный форвард ТОЛЬКО в
  loopback-диапазон 8120–8129 и ничего больше. **Ротация:** пересоздать `dist/tunnel_key`, обновить
  `/home/tunnel/.ssh/authorized_keys` (public key), новый `dist/token` (+ web-путь), `bash build_and_deploy.sh`.
